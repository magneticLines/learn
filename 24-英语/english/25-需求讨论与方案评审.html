需求讨论与技术方案评审：讲清 trade-off

比 code review 难一档，因为它要求更长的论证链条 —— 不只是"这里该改"，而是"为什么选 A 不选 B，代价是什么，什么条件下会变"。这一节的核心技能是结构化表达：让一段两分钟的技术论证有骨架、有取舍、别人听得下去。

PART 1 学习资料 读完再动手 · 约 25 分钟

为什么这个场景特别难

standupcode review方案评审
时长30 秒一两句1–3 分钟连续说
结构要求固定三段单点需要自己搭骨架
语言需求三个时态强度控制因果、条件、对比、让步
失败后果信息不清伤人或被忽略方案被否，或者被误解成别的意思

关键难点是连续说 1–3 分钟不断。standup 有模板，code review 是碎片，方案评审要你把一个完整论证组织出来 —— 而这时你的工作记忆已经被内容占满了（回到 W15 的容量问题）。

解法是把结构预制成模板，让骨架不占工作记忆。

你说中文讲方案时也有隐含结构（问题 → 方案 → 代价 → 结论），只是从没显式化过。把它显式化并配上固定句式，就等于把结构从"现场生成"变成"调用预制件" —— 省下的槽位全给内容。

这和 W15 讲的语块是同一个原理，只是尺度更大：语块是句子级的预制件，结构模板是段落级的预制件。

核心模板：五段式技术论证

段说什么句式时长
① 定问题我们要解决的到底是什么The problem we're trying to solve is ...15 秒
② 给结论先说结论，不要吊着I'd go with X. / My recommendation is ...10 秒
③ 说理由两到三条，不要更多Mainly for two reasons. First ... Second ...40 秒
④ 认代价最关键的一段The trade-off is ... / The downside is we'd lose ...30 秒
⑤ 定边界什么条件下这个结论会变If X changes, I'd reconsider.15 秒
第 ④ 段是本节最重要的部分，也是最多人跳过的。

主动说出方案的代价，会带来三个效果：显得你考虑周全（而不是只会推销自己的方案）、抢先回答了别人要问的问题、把讨论从"对错"变成"取舍" —— 后者才是技术讨论该有的形态。

只讲优点的方案陈述，在英美技术团队里会立刻被质疑。"So what's the catch?" 是标准反应。不如你自己先说。

四类必备语块

① 表达取舍（本节核心）

用法句式
标记取舍The trade-off is ... / The cost of that is ...
换取关系We'd be trading X for Y. / We gain X at the cost of Y.
承认缺点The downside is ... / It's not free — we'd have to ...
判断值不值I think that's a fair trade. / I don't think that's worth it.
两者都不好Neither option is great, but X is the lesser evil.

② 表达条件与依赖

It depends on whether ...（要跟上具体依赖什么，不能只说 it depends）/ As long as X holds, ... / Assuming we have ..., then ... / If the traffic grows past X, this breaks down.

注意 It depends. 单独说出来是零信息量，而且在英美职场会被视为回避问题。必须紧跟"依赖什么"：It depends on how much write traffic we expect.

③ 对比方案

Compared to X, Y gives us ... / The main difference is ... / X is simpler, but Y scales better. / Both work, but X is easier to roll back.

④ 让步与坚持

让步：That's a fair concern. / You're right that X is a risk. / I hadn't thought about that.
坚持：I still think X is the right call because ... / I hear you, but the bigger risk is ...

先让步再坚持，是最有效的说服结构 —— That's a fair concern, and you're right about the latency. But I think the bigger risk is ...

需求讨论：另一套技能

方案评审是你输出，需求讨论主要是提问和确认。核心是把模糊需求问清：

要澄清的问法
真实目标What are we actually trying to achieve here? / What does success look like?
优先级If we can only do one of these, which one?
量化模糊词By "fast", are we talking under a second or under 100ms?
边界Is X in scope for this, or a follow-up?
约束What's the hard deadline, and what's flexible?
确认理解Let me play that back: you want ... — is that right?

What does success look like? 是需求讨论里最有价值的一句话 —— 它把抽象需求逼成可验证的标准，而且母语者会觉得你很专业。

常见陷阱

  • 不说代价，只讲优点。本节头号问题。英美技术团队会立刻问 "What's the catch?"，不如你自己先说。
  • 结论放最后。中文习惯是铺垫后给结论，英语职场习惯是结论先行。铺垫太久对方会失去耐心，或者中途插话打断你的论证。
  • 理由给太多。五条理由不如两条有力的。多余的弱理由会拉低整体说服力，对方会攻击最弱的那条。
  • 只说 It depends 就停。零信息量，而且像在回避。必须跟上依赖什么。
  • 不给边界条件。不说"什么情况下这个结论会变"，会让你的判断听起来像绝对主张，一旦有反例就整体崩。主动划边界反而更有说服力。
  • 被质疑就全盘让步。对方提一个顾虑，你立刻说 "OK, let's do it your way" —— 这在英美职场会被读作你本来就没把握。先让步再坚持。
  • 用书面语讲方案。你的方案文档写得很好，但口头讲的时候把书面句式说出来（Furthermore、It should be noted that）会很怪。
  • 没有结构，想到哪说到哪。技术内容本身很复杂，没有骨架的话对方会跟丢。五段模板的价值就在这里。

【你的角色】
一位有经验的技术评审者。你要**逐条攻击我的方案**，轮换以下攻击角度：
1. 质疑理由不成立（"你说它更快，有数据吗？"）
2. 提出我没考虑的场景（"如果并发上来十倍呢？"）
3. 推荐另一个方案（"为什么不用 X？它更简单"）
4. 质疑成本（"这要多久？值得吗？"）
5. 质疑可维护性（"半年后还有人懂这个吗？"）
6. **拿一个真实存在的缺点攻击**（如果我的方案确实有明显代价）
7. 质疑我的判断依据（"你以前做过类似的吗？"）
8. **不讲道理的反对**（"我就是不喜欢这个方案"）—— 练怎么应对非技术性反对

【我需要练的三种反应，你要评估我选得对不对】
A. **让步**：对方说得对，我该承认并调整
B. **坚持**：对方的顾虑不成立或不是主要矛盾，我该说清为什么
C. **妥协**：双方都有道理，给一个折中或分阶段方案

【每轮评估】
1. 我选的反应类型（A/B/C）对不对？如果错了，说明该选哪个、为什么
2. 我的让步是不是过度？（一被质疑就放弃是最常见的问题）
3. 我的坚持有没有实质内容？还是只是重复原来的理由
4. 我有没有用"先让步再坚持"的结构？
   （That's a fair concern... but I think the bigger risk is...）
5. 我有没有提出妥协方案？
6. 语言层面：情态动词用对了吗（would/could/might 表假设）、
   有没有中式表达、语气是防御性的还是专业的
7. **第 8 轮专项**：面对不讲道理的反对，我的处理是否得体？
