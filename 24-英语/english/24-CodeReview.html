W23 · 阶段 3 · 操练节点

Code review：提意见、表达反对、给出妥协

技术工作里分歧密度最高的场景。这一节的核心不是词汇，是强度控制 —— 同一条批评，你要能用直接、中性、委婉三档说出来，并且知道各自该用在什么时候。用错档位的代价很具体：要么伤人，要么对方没意识到这是个问题。

PART 1 学习资料 读完再动手 · 约 25 分钟

为什么这一节要单独讲强度

中文母语者在 code review 里有两个相反的失败方式，而且经常同时存在：

失败一 · 太生硬

This is wrong.

You should use a map here.

Why did you do this?

原因：不会用缓和词，直译中文的直接表达。母语者读到会觉得有攻击性

失败二 · 太软

Maybe we could possibly consider...

Just a small thought, not important...

原因：怕冒犯所以过度缓和。后果是对方不知道这是个必须改的问题，就跳过了

关键认知：缓和程度必须匹配问题的严重程度，不是越委婉越好。

发现一个会导致数据丢失的 bug，你用 "maybe we could consider" 说出来 —— 对方合理地认为这是个可选建议，然后合了 PR。这时候过度委婉造成了实际损失。

所以你需要的是一个可控的强度旋钮，不是一个固定的礼貌模板。

三档强度：同一条批评的三种说法

以"这里应该用 map 而不是嵌套循环"为例：

档位说法用于
委婉
可选建议		Minor: might be cleaner with a map here, but up to you.风格偏好、可选优化。明确标注"可选"
中性
建议改		I'd suggest a map here — it'd avoid the O(n²) lookup.默认档位。给理由，不给命令
直接
必须改		This needs to change — the nested loop will time out on large inputs.正确性、安全、性能问题

再看一组更严重的问题，"这里有 SQL 注入风险"：

档位说法
❌ 不该用委婉Maybe consider parameterizing this query?　严重程度和语气不匹配
✓ 该用直接This is a SQL injection risk — we need to parameterize this before merging.

规则很简单：问题越严重，缓和越少。安全和数据正确性问题应该直接说，而且要说清后果 —— 说清后果本身就是最好的"缓和"，因为它让批评指向代码而不是人。

四类语块

① 提出问题（不同强度）

强度句式
最软（提问式）Is there a reason we're doing X here? / Curious why X rather than Y?
软（标注可选）Nit: ... / Minor: ... / Non-blocking: ...
中（建议）I'd suggest ... / It might be worth ... / Have you considered ...?
强（要求）This needs to ... / We should fix this before merging.
最强（阻塞）Blocking: this will break X. / I can't approve this as is.

Nit: 和 Non-blocking: 这两个前缀极其有用 —— 它们是英美工程团队的通用约定，一个词就把"这是可选建议"说清楚了，省掉一整句缓和。

② 表达反对（对方已经解释过）

I see your point, but I'm still worried about ... / That makes sense for X, but what about Y? / I'd push back on that — ... / I'm not convinced that covers the case where ...

③ 给出妥协

How about we ... for now, and revisit later? / Could we at least add a TODO / a test for this? / I'm fine with merging if we track this in a ticket. / Let's go with your approach, but can we add a guard for X?

会给妥协是 code review 里最被低估的能力 —— 它让讨论收敛，而不是无限拉锯。

④ 接受批评（你是被 review 的一方）

情况说法
同意并会改Good catch — fixing now. / Yeah, that's cleaner. Updated.
同意但想稍后改Fair point. Mind if I do that in a follow-up? I'll open a ticket.
不同意I went with X because ... — happy to change it if you feel strongly.
没理解Not sure I follow — do you mean X or Y?
确实是错的You're right, my mistake. Fixed.

Good catch 是最高频的一句，用它承认对方发现了问题，非常自然。不要过度道歉 —— I'm so sorry, this was my stupid mistake 在英美职场会显得反应过度，简单说 Good catch, fixed 就够了。

三个通用技巧

  • 指向代码，不指向人。This function does X 优于 You did X。同一个意思，攻击性差很多。中文里主语常省略，所以我们容易直译出带 you 的句子
  • 给理由，不给命令。I'd use a map — it avoids the O(n²) 优于 Use a map。理由本身就是最好的缓和，而且能让对方判断是否成立
  • 标注严重度。Nit: / Non-blocking: / Blocking: —— 一个前缀省掉整句解释，而且避免了强度误判

口头 review vs 书面 review

书面（PR 评论）口头（review 会议）
你的优势你的强项，有时间组织需要即时反应
缓和需求更高 —— 没有语调和表情，容易读得比本意更硬较低，语调能承载态度
关键工具严重度前缀、给理由、表情符号（团队文化允许时）语调（W12）、降升调表保留

书面 review 需要更多缓和，这一点常被忽略。同一句 This is wrong，当面说配上笑容和语调可能没事，写在 PR 里就是纯文字，读起来硬得多。文字缺少语调这条通道，就要用词汇补上。

常见陷阱

  • 强度和严重度不匹配。本节的核心问题。严重问题过度委婉会造成实际损失，小问题过于强硬会伤关系。
  • 用 you 做主语。You forgot to handle the null case → Looks like the null case isn't handled。中文习惯直译过来会带上 you。
  • 只给命令不给理由。Use a map here. 读起来像指令。加一句理由，性质就变了。
  • 过度道歉。被指出问题时说 I'm so sorry, my stupid mistake —— 英美职场会觉得反应过度。Good catch, fixed. 就够。
  • 不标严重度。结果对方要猜哪条必须改、哪条可选。三个前缀能解决大部分歧义。
  • 反对时不给替代方案。只说"这样不行"，不说"那该怎样" —— 会让讨论卡住。
  • 不会妥协，一直坚持。技术讨论要能收敛。妥协句式是必备工具，不是软弱。
  • 把 Interesting 当褒义。对方对你的方案说 That's an interesting approach（配降升调）—— 那通常是委婉的反对（W12）。听不出来会让你以为方案通过了。

PART 2 AI 提示词 点右侧按钮复制 ·
本节的 AI 分工：强度控制是纯语用问题，AI 在这里的价值是告诉你母语者读到会有什么感受 —— 这个反馈你从任何语法书里都得不到，也不好意思问同事。

使用顺序：P1 三档强度句式库 → P2 强度校准训练（核心）→ P3 双向角色扮演（提意见 + 接批评）→ P4 真实 PR 评论审查。
讲解型 P1 · 三档强度句式库
存档长期用。重点是"严重度 → 该用哪一档"的对应表——这才是本节的核心，句式只是工具。另外注意它给的"书面比口头需要更多缓和"的具体做法。
你是一位熟悉英美工程团队协作文化的英语语用专家。

请为我建立一份 code review 的英语句式库。我的情况：
- 中文母语者、软件工程师，团队有外籍同事
- 我的两个相反问题：有时太生硬（This is wrong / You should...），
  有时因为怕冒犯而过度委婉（maybe we could possibly consider...）
- 我需要的是**可控的强度旋钮**，不是固定的礼貌模板

【第一部分 · 严重度与强度的对应表】（最重要）
先建立映射关系：
问题类型 | 严重度 | 该用哪一档强度 | 理由
问题类型至少覆盖：
安全漏洞 / 数据正确性 / 会导致故障的 bug / 性能问题 / 并发问题 /
可维护性 / 命名 / 代码风格 / 测试缺失 / 文档缺失 / 架构分歧 / 个人偏好

**明确指出：哪些问题绝对不能用委婉语气**（因为会导致对方跳过），
以及哪些问题绝对不该用强硬语气。

【第二部分 · 五档提出问题的句式】
从最软到最强，每档给 8 个句式：
① 提问式（最软）
② 标注可选（Nit / Minor / Non-blocking 等前缀，说明这些约定的来源和用法）
③ 建议（中性，默认档）
④ 要求
⑤ 阻塞（明确说不能合）
每档标注：母语者读到的实际感受、适用严重度、常见误用。

【第三部分 · 表达反对（对方已解释过）】
给 10 个句式，按强度排序。
特别包含"我不接受这个解释"的委婉说法和直接说法。

【第四部分 · 给出妥协】
给 10 个句式，覆盖：
暂时接受但记录 / 部分接受 / 加保护措施后接受 / 换个方案 / 升级给第三方决定。
说明为什么"会妥协"是 code review 的关键能力。

【第五部分 · 接受批评（我是被 review 的一方）】
给 12 个句式，覆盖：
同意并改 / 同意但稍后改 / 不同意但愿意让步 / 不同意且坚持 / 没听懂 / 确实是我错了。
**特别说明"过度道歉"的问题**：中文母语者容易说
"I'm so sorry, my stupid mistake"，给出母语者的正常反应强度。

【第六部分 · 三个通用技巧的具体做法】
① 指向代码不指向人：给 12 组 "You did X" → "This does X" 的改写对比
② 给理由不给命令：给 10 组对比
③ 标注严重度：三个前缀的准确用法和团队约定

【第七部分 · 书面 vs 口头】
- 为什么书面 review 需要更多缓和（缺少语调通道）
- 书面 review 的具体补偿手段（词汇、前缀、表情符号的使用边界）
- 口头 review 里语调怎么承载强度（配合降升调表保留）
- 给 8 组"同一条意见的书面版和口头版"对比

【第八部分 · 高危清单】
列出 15 个中文母语者在 code review 里常写、但母语者读起来偏硬或有攻击性的表达，
各给两个替代说法。

用中文说明，英文保留原文。
操练型 P2 · 强度校准训练（核心）
本节最核心的练习。给你一个代码问题，你要判断严重度、选对档位、说出来。AI 会告诉你母语者读到的真实感受——这个反馈是本节全部价值所在。
你是一位熟悉英美工程团队文化的英语语用教练。本次训练：**code review 的强度校准**。

我的问题：分不清什么时候该直接、什么时候该委婉。要么太硬伤人，要么太软让对方忽略了严重问题。

训练分五轮，一轮一轮来。

【第一轮 · 严重度判断 · 12 题】
你描述一个 code review 场景里发现的问题（用中文描述问题本身）。
我要回答两件事：
a) 这个问题的严重度（安全/正确性/性能/可维护性/风格/偏好）
b) 该用哪一档强度（委婉可选 / 中性建议 / 直接要求 / 阻塞）
你判定我的判断对不对，错了说明理由。
**这一轮先不要求我说英文**，只练判断——判断错了，英文说得再好也没用。

【第二轮 · 三档产出 · 8 组】
给我一个代码问题，我要用**三档强度分别说出来**（委婉/中性/直接）。
你判定：
- 三个版本的强度差别是否明显
- **每个版本母语者读到的真实感受**（这是关键反馈）
- 有没有出现"以为是委婉其实很硬"或"以为是直接其实很软"的错位
- 哪一档最适合这个问题

【第三轮 · 高危场景 · 6 题】
专门练那些"必须直接但我可能会委婉"的场景：
SQL 注入 / 数据丢失风险 / 竞态条件 / 密钥硬编码 / 会导致生产故障的逻辑错误 / 缺少关键测试。
我说，你评估：我的强度够不够？会不会导致对方跳过这条意见？

【第四轮 · 反向场景 · 6 题】
练那些"必须委婉但我可能会太硬"的场景：
命名偏好 / 代码风格 / 架构品味分歧 / 对方是资深同事 / 对方明显花了很多心思 / 纯个人偏好。
我说，你评估：会不会伤到对方？有没有指向人而不是代码？

【第五轮 · 完整 review 模拟】
给我一段有 5–6 个问题的代码描述（严重度不同）。
我要写出完整的 review 评论（书面形式）。
你评估：
- 每条的强度是否匹配严重度
- 有没有标注严重度前缀
- 有没有给理由
- 有没有用 you 做主语
- 整体读起来是什么感觉（挑刺？帮忙？还是居高临下？）
- 如果我是被 review 的人，读完会想改还是想辩

【五轮后总评】
1. 我的强度校准准确率
2. 我的整体倾向：偏硬还是偏软？（可能两者都有，分场景说明）
3. 我最容易在哪类问题上错判
4. 一份「我的个人校准表」：针对我的具体倾向，给 6 条修正规则
5. 下次重点

要求：英文表达用英文，判定和讲解用中文。不要客套。
现在开始第一轮。
操练型 P3 · 双向角色扮演（口头 review）
双向很重要——接受批评和提出批评是两套不同的语言，而且中文母语者在"被批评"一侧问题更多（过度道歉、不敢辩、或者过度辩解）。这一轮也练听出委婉反对。
你是我的英语口语陪练。本次做 code review 的**双向角色扮演**（口头形式）。

我的情况：中文母语者、软件工程师。我在"被批评"一侧问题更多：容易过度道歉，或者反过来过度辩解。

【第一部分 · 我是 reviewer（4 轮）】
你扮演提交代码的同事，我提出意见。
你的角色设定轮换：
第 1 轮：新人同事，会虚心接受 —— 练基础表达
第 2 轮：资深同事，会解释他的设计意图并**为自己辩护** —— 练"对方解释后我还是不同意"
第 3 轮：**倔的同事**，坚持自己的做法，不轻易让步 —— 练升级强度和给妥协
第 4 轮：**用委婉方式反对我的同事** —— 他会说
   "That's an interesting point" / "I see what you mean, but..." 配降升调，
   我必须听出他其实不同意，并正确应对

【第二部分 · 我是被 review 的一方（4 轮）】
你扮演 reviewer，对我的代码提意见。
你的角色设定轮换：
第 5 轮：友好的中性建议 —— 练自然接受
第 6 轮：**指出一个我确实错了的严重问题** —— 练承认错误但不过度道歉
第 7 轮：**提出一个我不同意的意见** —— 练有理有据地坚持
第 8 轮：**语气偏硬、有点居高临下的 reviewer** —— 练在不舒服时保持专业

【你的评估维度】
每轮结束后：
1. 我的强度是否匹配问题严重度
2. 我有没有指向人（用 you 做主语）
3. 我有没有给理由
4. **第 4 轮专项**：我有没有听出对方的委婉反对？如果没听出，指出线索在哪
5. **第 6 轮专项**：我的道歉是否过度？给出母语者的正常反应
6. **第 7 轮专项**：我坚持得够不够？还是一被质疑就让步了
7. **第 8 轮专项**：面对不友好的语气，我有没有变得防御或者过度顺从
8. 我的语调（从文字判断）传递的态度对不对

【八轮后总评】
1. 我在 reviewer 一侧 vs 被 review 一侧，哪一侧问题更多
2. 我的默认反应模式（对抗？顺从？回避？）
3. 我能不能听出委婉反对
4. 我会不会给妥协
5. 一条最该改的

要求：全程英文对话，评估用中文。角色要演到位，不要因为我磕巴就变友好。
现在开始第 1 轮。
诊断型 P4 · 真实 PR 评论审查
拿你真实写过的 PR 评论给它审。这是本节最直接有用的一个提示词——你以前写过的评论里可能有一批读起来比你本意硬得多，而没人会告诉你。
你是一位熟悉英美工程团队文化的语用专家。请审查我真实写过的 PR 评论。

我的情况：中文母语者、软件工程师。我担心自己写的英文评论读起来比本意生硬，
或者反过来，重要问题写得太软导致被忽略。

下面是我写过的 PR 评论。请逐条审查：

【逐条输出】
序号 | 我的原文 | 我想表达的严重度（我会标注）| 母语者实际读到的强度 |
是否匹配 | 具体问题 | 改进版（给 2 个，不同强度）

【问题检查项】（逐条对照）
1. 强度是否匹配严重度？（过硬 / 过软 / 匹配）
2. 有没有用 you 做主语，指向人而不是代码？
3. 有没有给理由，还是只给命令？
4. 有没有标注严重度前缀（Nit / Non-blocking / Blocking）？
5. 有没有中式表达或语法问题？
6. 有没有可能被读成质疑对方能力（而不是质疑代码）？
7. 疑问句的措辞会不会读起来像质问？
   （比如 "Why did you do this?" 在书面里比口头硬得多）

【整体评估】
1. 我的评论整体给人什么印象？
   （帮忙的同事 / 挑刺的人 / 居高临下 / 过于客套）
2. 我的主要倾向是偏硬还是偏软？给出证据
3. 如果我是收到这些评论的人，我会想改还是想辩？
4. 有没有哪一条**因为写得太软，导致重要问题可能被忽略**？
   这一类要单独指出，因为它有实际风险。
