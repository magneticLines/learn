# 涌现式设计（Emergent Design）编码技能

遵循 Kent Beck 简单设计四规则编写代码，让良好架构从持续重构中自然涌现，而非一次性大设计。

## 适用场景

- 编写任何新功能代码时
- 重构既有代码时
- Code Review 时检查代码质量

## 核心规则（按优先级从高到低）

1. **运行所有测试** — 代码必须可被验证
2. **不存在重复代码（DRY）** — 每份知识在系统中只有单一表示
3. **代码表达程序员的意图** — 代码即文档，读者能直接理解
4. **尽量减少类和方法的数量** — 在前三条满足的前提下避免过度设计

## 规则详解

### 规则一：运行所有测试

- 写代码前先思考"这段代码怎么测试"
- 依赖通过构造器/参数注入，不硬编码 new
- 接口抽象让测试时可替换真实实现
- 如果发现一个类很难测试，说明它职责过重或耦合过紧——拆开
- 测试不只是验证，更是设计驱动力

### 规则二：不存在重复代码（DRY）

- 相同的逻辑散落多处 → 提取方法/类
- 相似的判断条件散落多处 → 提取为命名谓词方法
- 相同的魔法数字/字符串 → 提取为命名常量
- 隐式重复：不同类中实现了相似概念 → 提取统一抽象
- 三次法则（Rule of Three）：第一次直接写，第二次容忍，第三次必须提取

### 规则三：代码表达程序员的意图

- 好的命名胜过注释：`calculateMonthlyInterest()` 优于 `calc()`
- 每个函数只做一件事（20 行以内，能用一句话描述职责）
- 条件/循环中的魔法数字改为命名常量或封装方法
- 在命名中使用设计模式词汇：`PaymentStrategy`、`UserFactory`——模式名是团队词汇表
- 写代码时假设读者是暴力倾向的 psychopath 知道你住哪

### 规则四：尽量减少类和方法的数量

- 满足前三条之后才考虑——优先级最低
- 不要为"以后可能需要"的场景预先添加抽象（YAGNI）
- 能用语言内置特性（Function、Supplier 等函数式接口）解决的问题，不自己造接口/工厂
- 区分"必要的抽象"和"教条主义的抽象层"

## 工作流程

```
写代码 → ① 跑测试（验证正确）
       → ② 消除重复（提取抽象）
       → ③ 改善表达力（重命名、拆分）
       → ④ 删除多余的层（精简体量）
       → 再写代码 → 循环
```

每次小循环后代码都比之前更清晰、更正确、更精简。

## 落地检查清单

- [ ] 每一段逻辑都有测试覆盖？
- [ ] 依赖是否通过外部注入而非硬编码？
- [ ] 相同概念是否只在一处定义？
- [ ] 函数/变量名是否揭示了意图而非实现方式？
- [ ] 每个函数是否不超过 20 行、只做一件事？
- [ ] 抽象层次是否刚好满足当前需求（不超前、不欠债）？
- [ ] 如果删除一条注释，代码本身是否依然清晰？
